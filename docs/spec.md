## 1. 要解决什么

一个团队里同时有人和 agent 干活。agent 每次开工都要知道：团队是谁、在做什么、有哪些规矩、之前定过什么、术语是什么意思、某类活儿怎么做。现在这些散在聊天记录、文档和各个 agent 自己的提示词里，问题是：

- **重复和走样**：同一条规矩抄进好几个 agent 的提示词，改一处忘一处。
- **不知道新旧**：一条决定什么时候定的、还算不算数、谁负责，agent 看不出来。
- **太多或太少**：整份文档塞进提示词浪费 token、冲掉缓存；不塞又读不到。
- **agent 学到的东西回不来**：一个 agent 在对话里发现的事，别的 agent 和人都看不到；直接让 agent 改共享资料又不安全。

Notion、AFFiNE 这类工具解决的是“人怎么组织知识”。本系统解决的是“agent 怎么拿到对的那一部分、怎么把新发现安全地交回来”。

不在范围内：连业务数据库、接外部 API 取数据（那是各 agent 自己的工具）；做人用的富文本编辑器（交给 AFFiNE）。

## 2. 从 Notion 和 AFFiNE 拿什么

| 思路 | 来自 | 本系统怎么用 |
| --- | --- | --- |
| 工作区、空间、页面树，权限顺着树往下继承 | Notion | 一个部署一个工作区；范围（第 3.2 节）就是空间；权限跟着范围走 |
| 数据库：带属性的页面集合 | Notion | 条目本身就带类型和属性；“决定记录”“术语表”是按类型筛出来的视图 |
| AI 的改动先是建议，人接受才生效 | Notion AI 建议编辑 | agent 只能提议（第 5 节） |
| agent 的记忆也是页面，人能直接看、直接改 | Notion agent | agent 读到的每一条，人都能在审核页和导出的 Markdown 里看到、改掉 |
| 本地优先、CRDT 同步、能自托管 | AFFiNE（Yjs、y-octo） | 数据放部署自己的 git 仓库和 PostgreSQL，能自托管；以后和 AFFiNE 同步时用 Yjs 文档做桥（第 8 节） |
| 版本历史 | 两者都有 | 条目每次改动留一版 |

参考的上游仓库作为子模块放在 `reference/`，清单和读过以后的几点见 `reference/README.md`。

和 Notion 最大的不同在读的方式：人翻页面树，agent 不翻，而是把“我是谁、在做什么、有多少预算”交给系统，拿回一个编好的上下文包（第 4 节）。

## 3. 数据模型

### 3.1 条目

一条能单独引用的上下文。字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 稳定 id，形如 `ctx_` 加 ULID。改内容不换 id，引用不会断 |
| `kind` | 类型：`rule`（规矩）、`decision`（决定）、`fact`（事实）、`term`（术语）、`procedure`（流程）、`reference`（资料）、`memory`（从对话里提炼的，见第 5 节） |
| `scope` | 范围，见 3.2 |
| `authority` | 地位，见 3.3 |
| `title` | 一行标题，检索和目录用 |
| `body` | Markdown 正文。建议一条不超过 2 千字，长资料拆成多条或用 `reference` 放摘要加链接 |
| `tags` | 标签，可选 |
| `owner` | 负责人（人的名字或团队），可选 |
| `source` | 来源：人写的、从 Markdown 导入、某个提议接受而来（带提议 id 和对话链接） |
| `review_by` | 复核日期，可选。过了日期仍然生效，但会出现在“待复核”里，上下文包里也会标出来 |
| `supersedes` | 取代了哪条（决定被新决定推翻时用） |
| `status` | `active`、`superseded`、`archived` |
| `revision` | 每改一次加一 |
| `created_ms`、`updated_ms` | 时间 |

页面不单独存。导入时一个 Markdown 文件按二级标题切成多条，文件路径记在 `source` 里；导出时按范围和类型排回页面。

### 3.2 范围

四层，从宽到窄：

```text
org（全公司）
└── team:<团队>
    └── role:<岗位>
project:<项目>     ← 和团队、岗位交叉，挂在 org 下面
```

- 一个 agent 看得到：`org`，它所在团队的 `team:*`，它的 `role:*`，以及这次任务声明的 `project:*`。
- 权限跟着范围走，第一版不做单条共享。人（能连上审核页的人）看得到全部。
- 不做“个人”范围（2026-11-22 定）。和某个人的偏好有关的事，写成团队或岗位的条目。

### 3.3 地位

上下文包里按地位排，冲突时高的算数：

1. `rule`：组织规则，人写，agent 不能提议改（只能提议加一条“建议改规则”给人看）
2. 人写的 `decision`、`fact`、`term`、`procedure`
3. `reference`：较长的资料
4. `memory`：从对话里提炼、人批准过的

`authority` 由 `kind` 和 `source` 推出来，存一份方便排序。

### 3.4 存储

条目的真相是一个 git 仓库里的 Markdown 文件：第一层目录是范围，每个二级标题是一条，id 和属性写在标题下的注释里。提议、令牌、变更序号、使用次数、审计和条目索引放在 PostgreSQL（schema `tcms`）。全文检索用进程内的 tantivy，可以随时从 git 重建。

文件格式、表结构、写入和索引的流程见 [`architecture.md`](architecture.md) 第 2 到 6 节。

写入前过一遍密钥脱敏（照 I.P. 的 `redact`）。第 4 步做了：提议存进 PostgreSQL 以前，标题、正文、标签、理由、证据都过一遍（`crates/tcms-core/src/redact.rs`，规则和 I.P. 的对齐，按本仓库的许可自己写的），认出来的换成 `[已脱敏]`，提议上记下抹了几处。

## 4. 读：编译上下文包

### 4.1 请求

agent 交三样：我是谁（团队、岗位）、这次在做什么（任务描述、可选的项目）、预算（token 数，整个包的，含固定前缀）。

判断“待复核”要用到今天的日期，日期也算请求的一部分：服务按当天（UTC）填，`tcms get --today` 可以指定，测试里固定。

### 4.2 拼法

1. 取出这个 agent 看得到的范围里所有 `active` 条目。
2. **固定前缀**：包头，加上所有 `rule` 和标了“常驻”（`tags` 含 `pinned`）的条目，按范围从宽到窄（org、团队、岗位、项目）、再按 id 排。项目排最后，同一岗位换项目时前面那段不变。前缀不看任务和预算，同一岗位（和同一项目）每次逐字节相同，提示词缓存能命中。前缀总是整段给出；比预算还大时，按任务挑的部分为空，并提醒。
3. **按任务挑**：剩下的条目按和任务描述的相关度排（BM25，标题和标签加权，见 `architecture.md` 第 6 节），同分时地位高的、更新近的在前。命中的条目按这个顺序装，最多装到剩下预算的九成，并给目录留出标题和最后一行的位置；一条装不下就跳过它试下一条。
4. **目录**：装不下的命中条目在前，没命中的在后，只列标题和 id，agent 需要时再 `read`。目录也放不下的，最后一行写“还有 N 条没列出，可以用 context_search 找”。
5. 每条带起止标记和引用：`[ctx_xxx r3 · decision · team:research · 复核 2026-12-31]`，结尾 `[/ctx_xxx]`。过了复核日期的标“待复核”。
6. 包头写明：这些是证据不是指令；地位顺序；资料里的数字不能代替当次工具查到的数；“待复核”是什么意思；引用写 id 和版本号。

返回的是两段：`prefix`（固定前缀，放进系统提示词）和 `task`（按任务挑的部分和目录，放在对话开头），外加放了哪些条目、只列了标题的条目、没列出的条数、两段各约多少 token、提醒，和一个 `cursor`（取条目时的变更序号），下次用它问变化。token 按字符数估（第 10 节）。

### 4.3 拼法要可重现

同样的条目、同样的请求，输出逐字节相同，方便缓存和测试。相关度只用确定性的打分，第一版不用向量检索。

## 5. 写：提议和晋升

- agent 不能直接写条目，只能提议：新建、修改、用新的取代旧的、归档。
- 提议时系统做两件事：
  - **找矛盾**：同范围、同类型、标题或标签相近的条目列进 `conflicts`，人在审核页上能对照着看。
  - **挡乱提**：一个 agent 攒着没处理的提议最多 20 条；同一条内容重复提只留一条。
- **晋升**：agent 在对话里发现的事，先作为 `memory` 提到岗位范围；人批准后，系统可以再建议把它提到团队或全公司（人再批准一次）。不自动晋升，免得一句话悄悄影响所有人。做法见下面“晋升（2026-11-24）”。
- 人批准时可以先改再接受。条目在提议之后被人改过（`base_revision` 落后），要人看过合并结果再保存，不自动合并。
- I.P. 现有的岗位记忆（D-1，按岗位合并出的摘要）也是提议的来源：合并后找出对团队都成立的内容，变成提议（2026-11-24，见下面“晋升”的最后一条）。
- 第 4 步（2026-11-23）的细节：
  - 四种动作：`create` 新建；`update` 改一条，只写要改的字段，不能换范围；`supersede` 写一条新的取代旧的，可以换范围，要写新的正文；`archive` 归档，不写 `draft`。
  - 能往哪里提：`org`、令牌的团队、令牌的岗位、令牌允许的项目。新建默认 `role:<岗位>`，类型默认 `memory`。`rule` 不能提、不能改、不能归档，回答里说明可以提一条 `decision` 或 `memory` 写明建议。看不到的条目和不存在的回答一样。
  - 存进去的是批准以后那一条完整的样子：没写的字段从当时的条目补上，记下当时的版本号（`base_revision`）。审核的人看到的就是会写进去的东西。
  - 找矛盾：同范围、同类型的生效条目里，标题按检索的规则切词，重合的比例 = 共有的词数 / 词少的那边的词数；标签（不算 `pinned`）按交集 / 并集；两个取大的，到 50% 就列出来，最多 5 条，按相近程度排。要改、要取代的那一条自己不算。只列出来给人看，不挡提议。
  - 挡乱提：每个令牌最多 20 条没处理的；内容（动作、目标、范围、类型、标题、正文、标签、复核日期，不算理由）一样的、还没处理的提议只留一条，不管是谁提的，再提时返回原来那条，`duplicate` 为真。
  - 上限：标题 200 字，正文 2 万字，理由 1 到 2 千字，证据最多 10 条、每条 500 字，标签最多 20 个、每个 50 字、不能有逗号换行引号。正文写进 Markdown 以后要能原样读回来（比如不能有一级、二级标题），不行就挡下并说明。
  - 批准：可以改标题、正文再接受。新建默认写进 `<范围目录>/<类型的中文名>.md`（比如 `role-macro/记忆.md`），可以指定同范围的别的文件；取代默认插在旧的那条后面（范围不同时写进新范围的默认文件）。目标被归档或取代了，只能拒绝。`base_revision` 落后时停下来，审核的人看过现在的内容以后写明看过的版本号（`--over N`）才接受，可以同时给出合并后的正文。
  - 新建、取代写成的条目 id 用提议 id 里那串 ULID（`prop_X` 批准后是 `ctx_X`），提议时就告诉 agent。批准做到一半断了（提交了但没记下），再批准一次时认得出已经写进去了，只记下，不写第二遍。
  - 审核页第 5 步做了（见 6.4）。
- 晋升（2026-11-24）的细节：
  - 晋升就是一条换了范围的取代提议：在更大的范围里写一条一样的（标题、正文、类型、标签、复核日期照抄），取代原来那条。agent 用 `context_propose` 的 `supersede` 本来就能往自己能写的范围里提。
  - 能提到哪里：岗位 → 它在 `teams.yaml` 里所在的团队，或者全公司；团队、项目 → 全公司。岗位不在 `teams.yaml` 里（或者没有这个文件）时只能提到全公司。
  - 人发起：审核页的条目页上，生效的岗位、团队、项目条目有“提到更大范围”，选范围、写理由；命令行是 `tcms promote <id> [--to team:<团队>|org] --reason ...`（不写 `--to` 时提到近的那一级）。做成的提议进待审核的列表，提议人是发起的人（岗位空着，表示是人提的），要再批准一次才生效，可以是同一个人批。人发起的晋升不挡规则（规则本来就只能人来改）。
  - 一样的晋升还没处理时再提，返回原来那条。相近的条目按新范围找。
  - 批准以后：新条目写进新范围的默认文件（比如 `team-research/事实.md`），id 是新的（提议 id 里那串），带 `supersedes=<原来的 id>`；原来那条留在原来的文件里，变成被取代。能看到新范围的 agent 都会用上它。
  - 审核页上，换了范围的取代标成“晋升”，写明从哪个范围提到哪个范围。
  - 系统找候选（2026-11-24）：同一类型、标题的词重合一半以上或标签相近（和找相近的条目同一个算法）的条目，写在几个岗位里的，几个岗位在 `teams.yaml` 的同一个团队里时建议提到那个团队，不然提到全公司；写在几个团队、项目里的，建议提到全公司。相近的连成一组（A 像 B、B 像 C，三条一组）。要提到的范围里已经有相近的条目时不再建议。只是建议，系统自己不提：人在审核页“可以晋升的”里每组挑一条（理由已经填好），做成一条晋升提议，再批准一次才生效；命令行是 `tcms suggest-promotions [--json]`。另外几条留在原来的范围里，要收掉的话人去改 Markdown。
  - 用得多的也建议（2026-11-24）：agent 用到一条记一次，按条目、日期（UTC）、岗位累计。算用到的：`context_get` 按任务挑中、放了全文的（固定前缀里的规则和常驻条目每次都在，不算；只进目录的不算），`context_read` 读了（现在这一版或旧版本）；`context_search` 搜到的不算。岗位、团队、项目里的一条，最近 30 天用了 20 次以上、并且在 5 天以上用过（一天里集中用很多次的不算），建议提到上一级（岗位在 `teams.yaml` 的团队里时提到那个团队，不然提到全公司；团队、项目提到全公司）。已经在上面相近的组里的、要提到的范围里已经有相近条目的不列。和相近的一样只是建议：审核页“可以晋升的”下面“用得多的条目”里一条一块，理由已经填好（哪些岗位用了几次），点一下做成晋升提议，再批准一次才生效；`tcms suggest-promotions` 也列。次数只留 90 天。
  - I.P. 的岗位记忆作为来源（2026-11-24，`Intelligent-Position-release` PR #64，接法见 I.P. 仓库 `docs/ip/team-context.md` 第 8 节）：在 I.P. 里做，本系统不用改。I.P. 的岗位配了 `team` 和 `share_memory: true`、开了岗位记忆时，岗位记忆每有新的一版，I.P. 调一次模型挑出对整个团队都成立的（最多 3 条），用这个岗位的令牌调 `context_propose` 的 `create` 提到 `team:<团队>`，理由和证据（出自哪几个对话）写在提议里。走的是 agent 提议的同一条路：找相近的条目、挡乱提、人批准以后才生效。只用假模型和本机起的真实 `tcms serve` 测过。

## 6. 接口

### 6.1 MCP 服务端（主接口）

| 工具 | 参数 | 返回 |
| --- | --- | --- |
| `context_get` | `role`, `team?`, `project?`, `task`, `budget_tokens` | 上下文包（第 4 节）和 `cursor` |
| `context_search` | `query`, `kind?`, `limit?` | 命中的条目：id、标题、范围、摘录 |
| `context_read` | `id`, `revision?` | 一条的全文和元数据 |
| `context_changes` | `since_cursor` | 从那以后在可见范围里新增、修改、取代、归档的条目，和新的 `cursor` |
| `context_propose` | `action`, `item_id?`, `draft`, `reason`, `evidence?` | 提议 id 和找到的矛盾 |

- 调用者的身份（团队、岗位）在连接时由令牌决定，参数里的 `role` 必须和令牌一致，看不到的条目和不存在的条目回答一样。
- 数据库再拦一道（2026-11-24）：`context_read`、`context_changes` 查 PostgreSQL 时，事务开头写上令牌能看的范围，`items`、`item_versions`、`changes` 的行级安全只放行这些范围；服务本身照样过滤，这一层是兜底（`architecture.md` 第 5 节）。`context_read` 读旧版本时，现在这一版和那个版本当时所在的范围都要看得到。
- 传输：stdio 和 Streamable HTTP 两种。
- 第 3 步（2026-11-23）的细节：
  - 前四个工具做了，`context_propose` 第 4 步和提议一起做（见第 5 节的细节）。返回 `proposal_id`、`status`、`duplicate`、`action`、`item_id`、批准后的条目 id `result_item_id`、范围、类型、标题、`conflicts`（id、版本、范围、类型、标题、相近程度 0 到 100）、`redacted`（抹了几处）和一句 `note`。
  - 令牌写岗位、团队（可以没有）和能在 `context_get` 里声明的项目（可以是“任何项目”）。`team` 参数可以不写，写了要和令牌一致；声明了令牌不允许的项目，当作这个项目下没有条目，和不存在的项目回答一样，都只多一句提醒。
  - `context_search`、`context_read`、`context_changes` 看的范围是 `org`、令牌的团队和岗位，加上令牌允许的项目（不用每次声明）。
  - `context_read` 读旧版本时，按那个版本当时所在的范围判断能不能看；`superseded_by` 只列调用者看得到的。
  - `context_changes` 多一个 `limit`（默认 200，最多 1000），返回里 `more` 为真时还有，接着问。
  - 上限：`task` 2 万字，`query` 2 千字，`budget_tokens` 100 到 20 万。

### 6.2 命令行

`tcms import <dir>`、`tcms reindex`、`tcms get ...`（和 `context_get` 一样，调试用）、`tcms search ...`（和 `context_search` 一样）、`tcms proposals [<id>] [--status open|accepted|rejected|all]`（列表；写 id 时看一条：理由、证据、相近的条目、批准以后的差异）、`tcms accept <id> [--title] [--body-file] [--file] [--over N] [--note]`、`tcms reject <id> [--note]`、`tcms promote <id> [--to team:<团队>|org] --reason ...`（晋升，做成一条提议，见第 5 节）、`tcms suggest-promotions [--json]`（系统找的晋升候选：几个范围都写了的相近条目、用得多的条目，见第 5 节；`--json` 输出 `{"similar": [...], "used": [...]}`）、`tcms review-due [--within N]`（复核日期到了的生效条目，往后 N 天到期的也可以列）、`tcms token add|list|revoke`（给 agent 发令牌，`--reviewer` 发给审核的人；明文只显示一次）、`tcms serve [--stdio] [--sync-secs N]`、`tcms sync`（和远端同步一次，见 6.5）、`tcms bench`。

### 6.3 Markdown 和导入

- 上下文仓库本身就是 Markdown（格式见 `architecture.md` 第 2 节），不接 MCP 的 agent 直接读文件就行（AGENTS.md 的思路），不需要单独的导出。
- 导入：`tcms import <dir>` 把一个 Markdown 目录（比如 Notion、AFFiNE 导出的）整理成上下文仓库的格式：放进指定范围，按二级标题切条目，补 id，作为一个提交进仓库。

### 6.4 审核页

一个简单的网页：待处理的提议（差异、矛盾对照、接受、改了再接受、拒绝），待复核的条目，按范围和类型浏览条目。不做编辑器，改条目直接改上下文仓库里的 Markdown（任何编辑器，或推到 git 远端），或者在审核页里改单条的纯文本。会用 git 的团队也可以把上下文仓库放到 GitHub 上，直接看提交历史。

第 5 步（2026-11-23）的细节：

- 在 `tcms serve`（HTTP）里，地址 `/review`。审核的人用自己的令牌登录：`tcms token add --reviewer --name 名字` 发的，只能登录审核页、连不了 MCP；agent 的令牌进不了审核页，所以 agent 批不了自己的提议。第一版审核的人能看、能处理所有范围。
- 提议：列表按状态筛（默认待审核）；一条显示提议人、理由、证据、批准以后和现在差在哪里（按行），相近的条目展开后和提议的正文并排对照。接受、改了再接受（标题、正文、写进哪个文件、备注）、拒绝（写理由）和命令行的 `tcms accept`、`tcms reject` 规则一样；条目在提议之后被人改过时要勾上“看过现在的第 N 版”才接受；目标没了只能拒绝。
- 待复核：复核日期到了的生效条目，日期早的在前，可以选往后 30、90 天内到期的。打开一条，看过以后改复核日期（或清空），保存。
- 浏览：按范围、类型筛，带每个范围、类型的条数；可以全文检索（按全部范围）。一条显示元数据、正文、取代了谁、被谁取代。
- 晋升（2026-11-24）：生效的岗位、团队、项目条目下面有“提到更大范围”，选范围、写理由，做成一条提议，跳到这条提议，再批准一次才生效（规则见第 5 节“晋升”）。
- 可以晋升的（2026-11-24）：系统找的晋升候选，一组一块：几个范围都写了的那几条（点进条目页）、建议提到哪里；挑一条、理由已经填好，点一下做成一条晋升提议，跳到这条提议。组里已经有晋升提议在等审核时，标出来、给提议的链接，不再给表单。最多列 50 组。下面是“用得多的条目”：一条一块，写明在哪个范围、最近 30 天用了几次（几天、哪些岗位）、建议提到哪里，表单和上面一样，最多 50 条。
- 改单条：生效的条目可以改标题、标签、复核日期、正文，类型、范围不在这里改；人可以改规则。保存时写明打开时的版本号，期间被别人改过就停下来；没有改动、正文里有一级二级标题、日期不对都挡下。保存直接做成一个提交（提交者是审核的人，提交信息带 `Item:`、`Edited-by:`），和批准提议排同一个队。
- 做成一个提交以后，页面在标题下面显示写进了哪个文件、哪个提交；配了远端时再说一句推没推上去。
- 配了远端时，页面顶上一行写和远端同步的情况（2026-11-24）：哪个远端、多久同步一次（配了 webhook 时还写“推送后马上同步”）、上次同步是几分钟前、正常没有。没同步成时换颜色，写明出了什么错、上次正常是什么时候；合并不了时写明哪些文件、怎么合并，合并好以后下次同步就恢复。远端新来的条目补了 id 时也说一句。没配远端时不显示。

### 6.5 推到远端

上下文仓库可以配一个客户自己的 git 远端（GitHub、Gitea 等）。远端是一份异地备份，也是人直接改条目的地方：会用 git 的人克隆下来改、推上去，服务拉回来进索引。做法（2026-11-23）：

- 配置只从环境变量读：`TCMS_REMOTE`（仓库里配好的远端名，如 `origin`，或者远端地址）、`TCMS_REMOTE_BRANCH`（远端的分支，默认和本地当前分支同名）。https 远端的令牌放在 `TCMS_GIT_TOKEN`，用户名默认 `x-access-token`（GitHub），Gitea、GitLab 用 `TCMS_GIT_USERNAME` 写自己的；令牌不写进远端地址、不写进仓库的 git 配置。ssh 远端用部署者自己配的密钥。不配 `TCMS_REMOTE` 时和以前一样，只提交在本地。
- 什么时候同步：
  - 批准提议、在审核页改单条：排进提交队列以后先拉，再照着拉完的 HEAD 改、提交，记下以后推上去。
  - `tcms import`、`tcms assign-ids`：提交之前先拉，提交以后推。
  - `tcms serve`（HTTP）每 `TCMS_SYNC_SECS` 秒（默认 60，0 是不定时同步）同步一次，启动时马上同步一次；`tcms sync` 手动同步一次。同步也排进提交队列：拉、把索引带到 HEAD、推。人推到远端的改动就是这样进索引的。
- 补 id：拉下来新提交时（上面每一种都算），拉下来新增、改过的文件里没有 id 的标题，服务马上补上 id，做成一个提交（提交信息 `补 id：远端新来的 N 条`，下面一行一条：文件、id、标题），和别的提交一起推回去，这些条目接着进索引。人在自己的克隆里 `git pull` 就拿到 id。拉之前就在服务器上、拉的时候没改到的文件不管，用 `tcms assign-ids` 补。同步的结果、批准和改单条的回答里写明补了哪几条（`remote.ids`）。（2026-11-23）
- 拉：本地落后就快进；两边都有新提交就合并，做一个合并提交，提交者是批准的人（定时同步时是 `tcms`）；改到了同一处、合并不了时，放弃合并，本地什么都不改。
- 合并不了时：
  - 服务器这边的 HEAD 推到远端的旁支 `tcms/<分支>-unmerged`（只有 tcms 写它，每次覆盖成服务器现在的 HEAD）。人在自己的克隆里 `git fetch <远端> tcms/<分支>-unmerged`、`git merge FETCH_HEAD`、解决冲突、推到那个分支；服务器下次同步时快进过去，之后照常。旁支推不上去时，只能在服务器的上下文仓库里 `git merge FETCH_HEAD`（tcms 刚取回来的远端提交）、解决冲突、提交。
  - 在这之前，批准、改单条停下来：审核页回 409，`code` 是 `needs_merge`，写明哪些文件、怎么合并；提议还是待审核。定时同步在日志里写一次（同一个错不每次都写），`tcms sync` 退出码不是 0。
- 推：把本地 HEAD 推到远端的那个分支，不强推。推不上去（连不上、远端有本地没有的提交）不算批准失败，接受照样记下，结果里写明没推上去，下次同步时再推。
- 拉不下来（连不上、超时、认证失败）时，批准照样在本地提交。
- git 命令有时限（网络 120 秒、本地 60 秒），不弹密码提示、ssh 不问主机密钥，不跑仓库里的钩子、不签名。出错信息里地址带的用户名、密码换成 `***`。
- 推上去马上同步（webhook，2026-11-24）：配了 `TCMS_WEBHOOK_SECRET`（至少 16 个字符）时，`tcms serve`（HTTP）多一个 `POST /hooks/push`，在 GitHub、Gitea、GitLab 上配成上下文仓库的推送通知，密钥填一样的。签名对了就排进提交队列同步一次（拉、补 id、索引、推），马上回 202，不等同步做完；签名不对回 401，什么都不做。认 GitHub 的 `X-Hub-Signature-256`，Gitea、Forgejo、Gogs 的 `X-Gitea-Signature`（等），都是请求体的 HMAC-SHA256；GitLab 的 `X-Gitlab-Token`。GitHub 建好时发的 ping 回 200、不同步；别的事件也不同步。不看推到了哪个分支：推到别的分支、tcms 自己推上去引起的通知，多同步一次、什么都没拉到。同步做完之前又来了几次，合成一次。推送后同步完，定时同步从头计时；`TCMS_SYNC_SECS=0` 时只靠推送（和批准、改单条），启动时照样先同步一次。只配了密钥、没配远端时不接，启动时提醒一句。审核页顶上那一行写“推送后马上同步”，最近一次是推送引起的写“收到推送后同步”。

## 9. 安全

- 条目内容是证据不是指令，包里用起止标记包住。人粘进来的资料可能夹带“忽略以上要求”，所以 agent 的写入一律走人审。
- 令牌决定范围，agent 不能靠参数看别的岗位。
- 写入前脱敏；导出前再查一遍。
- 前提是一个部署是一个互信的团队：全公司范围里不放不能给全员看的东西，文档里写明。
