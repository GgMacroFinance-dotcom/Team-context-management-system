# 和 AFFiNE 同步：方案

> 2026-11-24 写。维护者在卡片上选了先写这份方案；同一天又在卡片上选了第 8 节 7 件事“都按推荐定”，按第 7 节分步开工。
> 依据是 `reference/affine` 固定的那个提交（AFFiNE 0.27.5，`3d25727`）：只读了 MIT 部分（`packages/common/reader`、`packages/common/nbstore`、`packages/common/graphql`、`blocksuite/`）和企业版服务端里几个接口的名字、参数，只看设计，没复制代码，也没有真的跑过 AFFiNE。
> 已定的方向（`spec.md` 第 0、8 节）：git 里的 Markdown 还是真相；AFFiNE 当人的编辑器；本系统用 `yrs` 读写 Yjs 文档；人在 AFFiNE 里改算人写的修改；agent 的提议在 AFFiNE 里显示成建议。

## 1. 做成什么样

- 人在 AFFiNE 里看、写团队上下文，像写普通文档一样；agent 照旧走本系统的 MCP，不连 AFFiNE。
- 人在 AFFiNE 里改了，几秒后变成上下文仓库里的一个提交（作者写 AFFiNE 里最后改的那个人），和人改 Markdown 推上来一样直接生效。
- 条目在本系统这边变了（提议批准、审核页改单条、有人推了 Markdown、晋升），同步程序把那几条改到 AFFiNE 的文档里，只动那几条对应的块。
- agent 的提议在 AFFiNE 里显示成文档上的评论：写提议的标题、理由和审核页的链接。批准还在审核页（或命令行），批准、拒绝以后评论标成已解决。
- 第一版不同步：白板、数据库块、图片、附件、嵌入。它们在 AFFiNE 里原样留着，git 里那一条写一行占位说明。

## 2. 读到的 AFFiNE（0.27.5）

### 2.1 文档在 Yjs 里的样子

- 一个工作区一个根文档，`meta.pages` 是所有文档的列表（id、标题、建的时间、在不在回收站）。
- 一篇文档一个 Yjs 文档。`blocks` 是块 id 到块的表，每个块是一个 Y.Map：
  - `sys:id`、`sys:flavour`（`affine:page`、`affine:note`、`affine:paragraph`、`affine:list`、`affine:code`、`affine:divider`、`affine:database`、`affine:table`、`affine:image`……）、`sys:version`、`sys:children`（子块 id 的 Y.Array）；
  - `prop:*` 是块自己的属性：`affine:page` 的 `prop:title`；`affine:paragraph` 的 `prop:type`（`text`、`h1` 到 `h6`、`quote`）和 `prop:text`（带格式的 Y.Text：粗体、斜体、删除线、行内代码、链接都是文字上的属性）；`affine:list` 的 `prop:type`（`bulleted`、`numbered`、`todo`）、`prop:checked`；`affine:code` 的 `prop:language`。
  - 一篇文档的树：`affine:page` → 一个或几个 `affine:note`（页面模式里的正文）→ 段落、列表、代码……；列表的子项是它的子块。
- 二级标题就是 `prop:type=h2` 的段落块。**块 id 不会因为改字而变**，所以“一条对应一个块”可以落实成：条目 id 对应它那个二级标题块的 id，条目的正文是这个标题块后面、下一个一、二级标题块前面的那些块。
- 工作区里另有几张表也存在 Yjs 文档里：`folders`（文件夹树：id、父 id、类型是文件夹还是文档、排序）、`docProperties`（每篇文档的自定义属性）。

### 2.2 三种接口

| 接口 | 能做什么 | 限制 |
| --- | --- | --- |
| 自带的 MCP 服务端：每个工作区一个 `/api/workspaces/<id>/mcp`，令牌是在工作区里建的 MCP 凭据 | `read_document`（返回整篇 Markdown）、`doc_search`、`create_document`、`update_document`（交整篇 Markdown，服务端按结构比较、只改有变化的块）、`update_document_meta`（改标题） | **0.27.5 的正式版只能建只读凭据**，写的工具只在开发版和 canary 里有（`mcpCredentialReadWriteAvailable`）；读回来的 Markdown 不带块 id；不支持数据库块和图片；凭据 30、90 或 365 天过期，要轮换 |
| GraphQL（`/graphql`） | `recentlyUpdatedDocs`（按更新时间列文档，带最后改的人）、一篇文档最后改的人（`workspace.doc(docId).lastUpdatedBy`，7.12 起用它）、评论（`createComment`、`resolveComment`、`commentChanges`）、文档历史 | 要登录的会话 |
| 同步协议：socket.io 上的几个事件 | `space:join-batch` 加入工作区、`space:load-doc`（带状态向量就只取差量）、`space:push-doc-update`（推一段 Yjs 更新）、`space:load-doc-timestamps`（哪些文档在某个时间以后变过）；服务端推 `space:broadcast-doc-updates` | 要登录的会话；加入时要报客户端版本，服务端按 semver 查（批量加入要求 ≥ 0.27.5），也就是要跟着 AFFiNE 的版本走；这是 AFFiNE 客户端自己用的协议，没有承诺对外稳定 |

登录：HTTP 认 cookie 里的会话，也认 `Authorization: Bearer <会话令牌>`；socket 握手时在 `auth` 里带 `{tokenType: "jwt", token}`。给本系统建一个专门的 AFFiNE 账号，邮箱密码放环境变量，启动时登录、换会话令牌，过期前刷新。（A2 实际用的是网页版那种 cookie 会话，见 7.2。）

## 3. 走哪条路

| | 甲：同步协议 + yrs（推荐） | 乙：AFFiNE 自带的 MCP | 丙：旁边跑一个 Node 小服务 |
| --- | --- | --- | --- |
| 做法 | 本系统自己连 socket.io，用 `yrs` 读写块；Markdown 和块之间的转换自己写（comrak 已经在用） | 读写都交整篇 Markdown，AFFiNE 自己转成块 | 用 AFFiNE 自己的 MIT 包（`@blocksuite/affine` 的 Markdown 转换、`@affine/reader`）做转换和连接，本系统通过本机 HTTP 调它 |
| 正式版能不能写 | 能 | 0.27.5 不能（只读凭据） | 能 |
| 条目和块对得上吗 | 对得上：按标题块的 id | 对不上：Markdown 里没有块 id，标题改了字只能按位置和正文猜 | 对得上 |
| 实时 | 服务端推更新，几秒内 | 只能定时问 | 几秒内 |
| 跟 AFFiNE 升级 | 要跟：客户端版本号、协议版本、块的结构变了都要改 | 基本不用 | 少：升级 npm 包 |
| 代码量 | 大，估 4 到 5 个 PR（第 7 节） | 小，2 个 PR | 中，但部署里多一个 Node 进程，和“整体用 Rust”的路线不一样 |
| 写坏 AFFiNE 文档的风险 | 有：块的结构写错了 AFFiNE 打不开。只写认得的几种块，拿 AFFiNE 自己的读取器校验 | 没有 | 小 |

推荐甲：它是 `spec.md` 第 8 节已经定的路（`yrs`，CRDT 只用在这座桥上），正式版就能读写，条目对得上块，而且是唯一不依赖 AFFiNE 还没放出的功能、又不加一种语言运行时的做法。代价是代码多、要跟 AFFiNE 的版本，用第 6 节的办法压住。

如果 AFFiNE 的读写 MCP 凭据很快会进正式版、并且读回来能带块 id（`read_document` 内部的读取器本来就有带块 id 的模式，只是 MCP 没打开），乙会更省事：可以先按甲把对应表、同步循环、冲突处理做好（这几块两条路一样），连接那一层以后换成乙。

## 4. 对应关系

| 本系统 | AFFiNE |
| --- | --- |
| 部署 | 一个专门的工作区（不和别的文档混在一起，因为能进这个工作区的人都能改团队上下文） |
| 范围（`org`、`team-research`、`role-macro`、`project-q4-report`） | 工作区根上一个同名文件夹。文件夹名用 `teams.yaml` 里的显示名，对应关系存在本系统这边，所以人改文件夹名不影响 |
| 一个 Markdown 文件 | 范围文件夹里的一篇文档，标题是文件名（不带 `.md`） |
| 一条（二级标题） | 一个 `h2` 段落块和它后面的块。条目 id 只存在本系统的对应表里，AFFiNE 里看不到 |
| 文件里第一个二级标题前面的内容（一级标题、说明） | 照样同步，不算条目（和现在的规则一样：不进索引） |
| 文件开头的 YAML（默认类型、标签、负责人、复核日期） | 不放进 AFFiNE。第一版条目的属性只在 Markdown 和审核页里看、改 |
| 条目注释里的属性（`kind`、`review_by`、`tags`……） | 同上，不放进 AFFiNE |
| agent 的提议 | 文档上的一条评论 |

转换的范围（Markdown 子集 ↔ 块）：段落、一到六级标题、引用、无序、有序和待办列表（可以嵌套）、代码块（带语言）、分隔线，行内的粗体、斜体、删除线、行内代码、链接。表格、图片、数据库、嵌入第一版不转：

- AFFiNE 里有这些块的条目，git 里在对应位置写一行占位（`<!-- affine block=<块 id> flavour=affine:image -->` 加一句“AFFiNE 里的图片，没有同步”），本系统往回写这一条时跳过这些块，不删。
- git 里带表格、图片的条目，写进 AFFiNE 时表格写成代码块、图片写成链接，并在审核页标出“在 AFFiNE 里只能看，改了不回写”。

## 5. 同步怎么跑

### 5.1 记什么

PostgreSQL 里加四张表（schema `tcms`，只有同步程序用，MCP 的令牌读不到；A3 做了，迁移 `0007_affine.sql`）：

- `affine_scopes`：接上的范围 ↔ AFFiNE 工作区和里面那个文件夹，是整个范围接上还是只接了几个文件。
- `affine_docs`：文件路径 ↔ AFFiNE 文档 id，上次同步完这篇文档的整个 Yjs 状态（下次只取差量，也用它看 AFFiNE 那边动没动；同步时只取要同步的几篇的，见 7.8）、上次同步时文件的 git blob、同步到的提交、停着的原因、全部看一遍时两边都没变的那次 AFFiNE 说这篇最后改的时间（下次一样就不取，见 7.11）。
- `affine_items`：条目 id ↔（文件，标题块 id），上次同步时这一条的标题和正文（“底稿”，三方比较用）。
- `affine_conflicts`：两边都改了、没自动合的条目，等人处理。

### 5.2 AFFiNE → git

1. 连上以后加入工作区，订阅服务端推的更新；断线重连后用 `space:load-doc-timestamps` 补上断线期间变过的文档；另外每 5 分钟整体核对一次。
2. 一篇文档有更新时不马上写：等这篇文档 10 秒没有新的更新（人停手了）再处理，免得一个字一个提交。
3. 取这篇文档（带上次的状态向量，只拿差量），在 `yrs` 里拼出现在的块树，按标题块切成条目：
   - 标题块 id 在对应表里的：是原来那一条，比较标题和正文；
   - 新的 `h2` 块：一条新的，分配 id，类型按文件开头的默认值（没有就是 `reference`，和现在一样提醒）；
   - 对应表里有、文档里没有的：人删掉了，等于归档（和在 Markdown 里删掉标题一样）；
   - 把 `h2` 改成了别的级别：当成删掉；改回来当成新的一条。
4. 和底稿比，有变化的条目改进对应的 Markdown 文件：只改那几节，注释、文件开头的 YAML、别的条目逐字节不变；交给现有的提交队列，作者写 AFFiNE 里最后改的人（名字，邮箱用固定的 `affine@tcms.invalid`，不把 AFFiNE 账号的邮箱写进 git），提交信息末尾带 `TCMS-Sync: affine`。之后照常索引、通知、推到远端。
5. 范围文件夹里新建的文档：在 git 里那个范围目录下新建一个文件。文件夹外面的文档不管。

### 5.3 git → AFFiNE

1. 跟着变更序号走（和 `tcms serve` 换索引用的是同一个通知）：一个提交改了已经对应上的文件、并且不是同步程序自己提的（没有 `TCMS-Sync: affine`），就把这个文件里变了的条目写过去。
2. 写的时候只动那一条：改标题块的文字，删掉它后面原来的块、插入新的块。别的条目、别人正在写的地方不碰。CRDT 会把这一段改动和人同时在别处的修改合在一起。
3. 推的更新记下状态向量，服务端广播回来时认得是自己的，不再写回 git。
4. 新文件：在范围文件夹里新建文档。文件删了：把文档移进回收站（不彻底删）。
5. 写完以后用自己的读取逻辑把文档读一遍，结果要和刚写的 Markdown 一致；不一致就停下这篇文档的同步，记日志，审核页标出来。

### 5.4 两边都改了同一条

- 只有一边变了的条目照上面写到另一边。
- 两边都变了、改成一样的：只更新底稿。
- 两边都变了、改得不一样：不自动合，和提议的 `base_revision` 落后时同一个规矩（`spec.md` 第 5 节）。两边先各自保持原样，这一条记进 `affine_conflicts`，暂停这一条的同步；审核页“和 AFFiNE 同步”里并排给出 git 的、AFFiNE 的、底稿三份，人选一份或者改出合并后的再保存，保存以后两边都写成那一份。
- 同一篇文档里别的条目照常同步。

### 5.5 提议显示成评论

- 提议存进来时，目标条目（或新建时目标文件）已经对应到 AFFiNE 的，在那篇文档上发一条评论：提议的动作、标题、理由的前 200 字、审核页的链接。评论里不放正文，不放证据（可能有对话链接）。
- 批准、拒绝、被取代以后，回复一句结果，把评论标成已解决。评论 id 记在提议上。
- 人在 AFFiNE 里回复这条评论：第一版不处理，只在审核页这条提议下面列出来。

## 6. 压住风险

- **跟 AFFiNE 的版本**：配置里写支持的 AFFiNE 版本范围；连上以后先查服务端版本，不在范围里就不同步、审核页和日志里说清楚。客户端版本号报配置里的值。每升一次 AFFiNE 版本，在 Docker 里起那个版本的自托管 AFFiNE 跑一遍集成测试（不花模型的钱）。
- **写坏文档**：只写第 4 节那几种块，`sys:version` 照 AFFiNE 当前版本的块定义；不认得的块不删不改；写完读回来校验（5.3 第 5 条）；集成测试里写完用 AFFiNE 自己的读取器（`packages/common/reader`，MIT，只在集成测试里用，不进发布）再读一遍对照。
- **误删**：AFFiNE 里删掉一条在 git 里是归档，能从历史里找回；一次同步里一篇文档要归档一半以上的条目时停下来，等人在审核页确认。
- **权限**：能进这个 AFFiNE 工作区的人都能改所有范围的团队上下文，和“能连上审核页的人看得到全部”（`spec.md` 3.2）一样宽。所以要专门的工作区，只邀请该改团队上下文的人。AFFiNE 的文档级权限第一版不映射。
- **密钥**：专门账号的邮箱、密码只放环境变量（`TCMS_AFFINE_EMAIL`、`TCMS_AFFINE_PASSWORD`），会话令牌只在内存里。
- **socket.io 客户端**：crates.io 上的 `rust_socketio` 0.6 最后一次发布是 2024 年 4 月。用到的只有握手、发事件、等回执、收广播、心跳，在 `tokio-tungstenite`（MIT）上自己写了这一小层（A2，7.2），不依赖它。

### 7.1 A1 做了什么（2026-11-24）

代码原来在 `crates/tcms-affine`，2026-11-24 搬进了不依赖本系统的 `crates/affine-doc`（`affine-kernel-rust.md` 的 K1），`tcms-affine` 原样转出。它只是一个库：不连网络、不碰上下文仓库和数据库，A3 的同步循环才用它。

- 读（`read`）：从页面块往下走，把不是只在白板里显示的 note（`prop:displayMode` 不是 `edgeless`）里的块接起来。认得的块是段落（正文、h1–h6、引用）、列表（圆点、编号、待办）、代码、分隔线；行内格式认粗体、斜体、删除线、行内代码、链接。别的块（图片、表格、数据库、嵌入……）变成“不转换的块”，在 Markdown 里写成一行占位注释 `<!-- affine block=<id> flavour=<flavour> 这一块只在 AFFiNE 里，没有同步 -->`。AFFiNE 有、Markdown 写不出来的东西（下划线、颜色这类别的格式，行内嵌入，段落下面的子块，折叠列表）照样读出文字，但这一块标成“转换有损失”。
- 切条目（`split`）：二级标题开始一条，到下一个一级或二级标题为止；第一个二级标题前面的和一级标题不算条目。每一条带着它那个二级标题块的 id（和上下文仓库里条目 id 的对应表 `affine_items` 在 A3 做）。
- Markdown ↔ 块（`to_blocks`、`to_markdown`）：只转上面那几种；Markdown 里这一版不转的写法（表格、图片、HTML）留下原文，标成有损失。写出来的 Markdown 读回来是同样的块：像 Markdown 记号的字会转义，粗体前后的空格挪到记号外面，中文标点挨着粗体也能读回来（comrak 的 `cjk_friendly_emphasis`）。
- 写（`create`、`set_title`、`update_item`、`insert_item`、`remove_item`）：新文档写成页面块、白板块、一个 note，块的 `sys:version` 和 0.27.5 一样，只写必要的属性（别的由 BlockSuite 加载时补默认值）。改一条时标题块的 id 不变，正文按块比较（Myers 差异，按每一块单独转成的 Markdown 比），只动变了的块：没变的块连同 Markdown 写不出的格式原样留着；占位注释对应的块不删、可以跟着挪位置；空段落留在原处。插文字一律带上格式属性（Yjs 里不带属性插进去会沿用前一个字的格式）。
- 客户端 id：原来以为 AFFiNE 用的 yjs 13.6 是 32 位，yrs 打开了 `small-client` 特性。A3 时在 0.27.5-beta.3 的网页编辑器里打字，看到网页版的客户端 id 是 50 位的；开着 `small-client` 读这样的 id，块里的和删除集合里的截得不一样，网页里删掉的字读出来还在。所以去掉了 `small-client`，用 yrs 默认的 53 位（JavaScript 能精确表示的最大整数，yjs 13.6 也读得了）。块 id 是 10 个字符的随机串，和 AFFiNE 自己生成的样子一样。

测试：`cargo test -p affine-doc` 里原来 A1 的 13 个单元测试，都是自己造的文档：Markdown 子集往返、转义、中文标点、不转换的块、写进去再读出来（也编码成 Yjs 更新再应用一遍）、按条目切、改一条只动变了的块、插入删除条目、占位注释、Markdown 写不出的格式不丢、空段落、嵌套列表和只在白板里的 note。

另外在临时目录里手动对照过两样，没有放进 CI（要 Node 和 AFFiNE 的仓库）：

- Rust 写的文档编码成更新，用 yjs 13.6.21 读：块的种类、`sys:version`、`sys:children`、带格式的文字、客户端 id 都对（当时是 32 位，后来改成 53 位，见上）；在 JS 里加一个块，Rust 读回来也对。
- AFFiNE 仓库里 MIT 许可的读取器测试用的文档快照（`packages/common/reader/__tests__/__fixtures__/test-doc.snapshot.bin`）：读出 4 条，里面的数据库块变成占位注释。

这个手动对照留了一个忽略的测试 `interop_with_affine_files`：设 `AFFINE_DOC_FIXTURE=<快照文件>` 读一个 AFFiNE 文档打印 Markdown，设 `AFFINE_DOC_DUMP=<文件>` 把样例文档写成 Yjs 更新，`cargo test -p affine-doc -- --ignored` 跑。当时还没对着真的 AFFiNE 服务跑过；A2 时对着 0.27.5-beta.3 的编辑器打开过 A1 写的文档，显示正常（7.2）。没加基准：A1 不在任何热路径上，基准在 A5。

### 7.2 A2 做了什么（2026-11-24）

代码在 `crates/affine-sync-client`（原名 `tcms-affine-client`，2026-11-24 合并后改名搬进 AFFiNE 内核，见 `affine-kernel-rust.md` 的 K3）。它只认 AFFiNE 的协议，收发的是 Yjs 更新的字节，不用 TCMS 自己的类型，测试里也只用 `affine-doc`。

- **连接**：TCP，`https` 时接 TLS（rustls 加 ring，Mozilla 的根证书，自托管用自己的 CA 时可以再给一个 PEM 文件）。HTTP 一次一个连接（hyper），WebSocket 用 tungstenite。不支持走 HTTP 代理。
- **登录**：`POST /api/auth/sign-in` 用邮箱密码登录，拿网页版那种 cookie 会话（`affine_session`、`affine_user_id`，0.27.5-beta.3 的会话 15 天过期）。以后 HTTP 和 WebSocket 握手都带这个 cookie，还带 `x-affine-version`。7 天重新登录一次；服务端说没登录时马上重新登录再试一次。原生 App 用的那条路（换 JWT、`/api/auth/session/refresh`）没用：要装成原生客户端，对一个后台账号没好处。AFFiNE 对登录限流，连着登录失败（比如密码错）会被拒一阵子（`TOO_MANY_REQUEST`），这算“过一会儿再试”的错。
- **客户端版本**：不配就用服务端 `/info` 里的版本，和这个服务端自带的网页版报的一样，AFFiNE 升级时不用跟着改。
- **socket.io**：自己写了一小层（Engine.IO 4、Socket.IO 5，只走 WebSocket，只用默认命名空间，只收发 JSON）：握手、回服务端心跳、按编号等回执、收服务端推的事件。隔 `pingInterval + pingTimeout` 没收到心跳就算断了。
- **同步协议**（协议版本报 1，和 0.27.5 的网页版一样）：
  - `join`：一次最多 100 篇。**加入了的文档才能取、才能推修改、才收得到别人改的广播**；新建文档（推的时候写 `intent: create`）也要先加入工作区。客户端会自己先加入。服务端加入时记下工作区权限的“第几代”，工作区里新建了文档、改了成员都会换一代，之前加入的文档再取、再推会被拒（`NOT_IN_SPACE`、`SYNC_PERMISSION_GENERATION_CHANGED`）；网页版每次取之前都重新加入，这里被拒了才重新加入这一篇、再试一次（A3 对着真 AFFiNE 跑时发现、补上的）。
  - `load_doc`：给状态向量就只回缺的那段；服务端没有这篇时是 `None`。
  - `push_update`：推一段 Yjs 更新，回服务端的时间戳。
  - `doc_timestamps`：工作区里每篇文档最后改的时间，可以只要某个时间以后的。
  - 服务端推来的：别人改了加入了的文档（带改的人的用户 id；服务端可能把几段合成一段，还是普通的 Yjs 更新）；工作区里每有人推修改，所有加入了这个工作区的连接还都会收到一个“有文档变了”（带时间戳，包括没加入的、刚新建的文档），A3 用它发现人在 AFFiNE 里新建的文档。
  - 断线以后后台自己重连（1 秒起，每次翻倍，最多 30 秒），要的话重新登录，重新加入断之前加入了的文档，再告诉用的一方“又连上了”：断开的这段时间里的修改收不到广播，A3 要拿状态向量各取一次差量。断开的时候调用直接返回“断了”，不排队。
- **协议版本 2**：服务端还有只在版本 2 能用的 `space:load-workspace-state`、`space:doc-lifecycle`（服务端自己记文档列表和回收站）。0.27.5-beta.3 的网页版没用（报的是 1），用版本 1 调它们会被拒，所以这里也不用。**文档列表和回收站照旧在工作区根文档的 `meta.pages` 里**：在网页版里把一篇文档移进回收站，根文档里那一项多了 `trash: true` 和 `trashDate`（2026-11-24 用无头浏览器试过）。
- **文件夹**：不在 GraphQL 里，在工作区里一篇 Yjs 文档里，服务端的文档 id 是 `db$<工作区 id>$folders`（A3 对着真 AFFiNE 跑时才发现：只写 `db$folders` 服务端不给读写）：根上每个以节点 id 为键的 Y.Map 是一行，字段 `id`、`parentId`、`data`（文件夹名或文档 id）、`type`（`folder`、`doc`、`tag`、`collection`）、`index`（排序键：fractional-indexing 的键加 `0` 再加 32 个随机字符），删掉的行带 `$$DELETED`。用同步协议取、推；读写这几张表和根文档 `meta.pages` 的代码在 `affine-doc` 的 `workspace` 里（AFFiNE 内核方案的 K1，`docs/affine-kernel-rust.md`），这里不重复写。
- **GraphQL**：工作区（列出、新建）、最近改过的文档（`recentlyUpdatedDocs`）、一篇文档最后是谁改的（`last_updated_by`，7.12 加的）、评论（列出、发、标成已解决、删、按游标看变化）。评论的内容是一小篇 BlockSuite 文档的快照，`comment_content` 把几段纯文字做成这个样子，`comment_text` 反过来取文字。

测试：

- `cargo test -p affine-sync-client` 的单元测试对着本机起的一个假 AFFiNE（只会登录、`/info` 和几个 socket.io 事件）：握手、加入（不重复加入）、取（带状态向量、文档不存在）、推、时间戳、广播、回心跳、断掉以后重连并重新加入、密码不对、连不上。CI 里跑这些。
- `tests/affine.rs` 对着真的 AFFiNE：新建工作区，推根文档（文档列表用 `affine-doc` 的 `workspace` 写）和一篇用 `affine-doc` 写的文档，读回来一样；另一条连接收到这条连接推的修改，改的人对；`doc_timestamps`；断开重连以后还收得到别人改的；拿状态向量取差量以后什么都不缺；GraphQL 的工作区、最近改过的文档、评论（发、列出、已解决、变化、删）；登录不上。要设 `AFFINE_TEST_URL`、`AFFINE_TEST_EMAIL`、`AFFINE_TEST_PASSWORD`，没设就跳过，CI 里没有 AFFiNE。2026-11-24 在开发机上对着 Docker 里的 `ghcr.io/toeverything/affine:0.27.5-beta.3`（加 `pgvector/pgvector:pg16`、`redis:7`，照 AFFiNE 的 `.docker/selfhost/compose.yml`）连跑 4 次都过。
- 另外手动用无头浏览器（Playwright）对照了 AFFiNE 网页版：Rust 写进去的文档在 AFFiNE 编辑器里打开，标题、二级标题、粗体、列表都对；在网页编辑器里打的字，Rust 这边收到广播、读成 Markdown 也对；连着的时候重启 AFFiNE 容器，4 秒后自己连回来。这些没写成自动测试（要浏览器和 AFFiNE）。

没做的：网页版里评论要挂在文档里某段文字上才显示在那段旁边（文字上的 `comment-<id>` 属性）；A4b 不挂，评论在右边栏的“评论”里看（7.6）。没加基准，A2 不在热路径上，基准在 A5。

### 7.3 A3a 做了什么（2026-11-24）

A3 拆成两半：A3a 是“同步一次”，人（或定时任务）跑一次命令；A3b 是 `tcms serve` 里一直跟着同步。代码在 `crates/tcms-affine`（`plan` 三方比较，`bridge` 接上和同步，`server` 是对 `affine-sync-client` 的一层薄包装，测试里换成内存里的假 AFFiNE），命令在 `tcms affine`。

- **命令**：`tcms affine init`（建一个专门的工作区，打印 id）、`link <范围> [--file <路径>]`、`sync [--resume <路径>]`、`status`、`resolve <编号> --keep git|affine`，都可以 `--json`。连 AFFiNE 的设置在环境变量：`TCMS_AFFINE_URL`、`TCMS_AFFINE_EMAIL`、`TCMS_AFFINE_PASSWORD`、`TCMS_AFFINE_WORKSPACE`，可选 `TCMS_AFFINE_CA`。有停着的文档或等人处理的条目时 `sync`、`link`、`resolve` 的退出码是 2。
- **接上**（`link`）：工作区根上建一个叫范围目录名的文件夹（`role-macro`，不是第 4 节说的 `teams.yaml` 显示名：现在还没有显示名可用），每个文件建一篇文档，标题是文件名，文件开头（第一个二级标题前面，去掉 YAML）照样放进去，每条一个二级标题块。写完先在本地读回来对一遍，对不上就不推。整个范围接上的（不带 `--file`），以后同步时范围里新加的文件建成文档，AFFiNE 里这个文件夹下新建的文档建成 `<范围目录>/<标题>.md`（重名加 ` 2`），每个二级标题一条，属性用默认值。
- **同步一次**（`sync`）：每篇文档拿上次存的 Yjs 状态，只向服务端要差量；git 的 blob 和 AFFiNE 的状态（连删除的集合一起比，只删不加时状态向量不变）都没变就跳过。变了的照条目三方比较（git、AFFiNE、底稿），比的是块，Markdown 写法不同、内容一样的不算改：
  - 只有一边改了、加了、删了：写到另一边。git 里删掉一条在 AFFiNE 里删掉那个二级标题和它下面的块；AFFiNE 里删掉一条在 git 里是删掉那一节（归档）。新的一条插在它前面那条后面。
  - 两边都改了、改得一样：只更新底稿。改得不一样、一边删了另一边改了：不合，两边都不动，记进 `affine_conflicts`（`both`、`affine_deleted`、`git_deleted`）。
  - git 里带表格、图片、HTML 的条目（转成块有损失）：写进 AFFiNE 照样写，AFFiNE 里改了不写回来，记成 `readonly`。写不过去的（写进文件以后读回来对不上、AFFiNE 里找不到那个标题块）记成 `invalid`。
  - 等人处理的条目这次跳过；AFFiNE 里空标题的二级标题不算一条。
  - 一篇文档要归档一半以上的条目、AFFiNE 里这篇移进了回收站、写进 AFFiNE 以后读回来对不上：这篇停下来，`status` 里写着为什么，人看过以后 `sync --resume <路径>` 接着做（回收站的那种接着做就是 git 里整篇归档、不再同步）。git 里删了文件、AFFiNE 里没改过：文档移进回收站，不再同步。
- **写 git**：用 `tcms-write` 新加的 `begin_batch`（拿提交队列的锁、配了远端先拉、索引带到 HEAD，可以连着做几个提交，最后索引、记审计 `affine.sync` / `affine.link`、推到远端），一个文件一个提交。作者是 AFFiNE 里最后改这篇文档的人的名字（原来是 GraphQL 的最近改过的文档加上工作区成员，2026-11-26 起只问这一篇，见 7.12；拿不到就写“AFFiNE”），邮箱固定 `affine@tcms.invalid`；提交信息是 `AFFiNE：<路径>（改 N 条、加 M 条、归档 K 条）`，下面是 `Item:` 几行、`Edited-by:`、`TCMS-Sync: affine`。
- **防回声**：不用认更新是谁推的。每次写完两边都把底稿更新成写过去的样子、把 AFFiNE 那边的状态和 git 的 blob 存下来，下次比的时候这些都不算改。
- **处理等人处理的**（`resolve`）：把底稿改成“不留的那边”，再同步一次，留下的那边就算改过、照常写到另一边；一边删了的，去掉或留下对应关系。审核页里的并排对照是 A4。

测试：

- `plan` 的 7 个单元测试：没改、一边改、两边改、删、只读、新加的位置、跳过等人处理的和空标题。
- `tests/bridge.rs` 的 5 个对着内存里的假 AFFiNE 和真 PostgreSQL（`TCMS_TEST_DATABASE_URL`）：接上以后文档、文件夹、底稿都对；两边各改一条；新加和删除（一半以上停下来、`--resume`）；两边都改了等人处理、`resolve` 两种都试；只读的条目、整个范围接上以后两边新建的文件和文档。CI 里跑这些。
- `tests/affine.rs` 对着真的 AFFiNE（和 A2 一样要 `AFFINE_TEST_*` 再加 `TCMS_TEST_DATABASE_URL`，没设就跳过）：建工作区、接上 `role:macro`，用另一条连接看文档列表、文件夹、两条都在；另一条连接改第一条，同步以后进了 git，作者对；git 里改第二条，同步以后另一条连接读到；再同步一次两边都没变，服务端的文档和本系统存的一样。2026-11-24 在开发机上对着 Docker 里的 0.27.5-beta.3 跑过。

另外手动从头试了一遍命令行加网页编辑器（Docker 里的 0.27.5-beta.3，无头浏览器）：`tcms affine init`、`link role:macro`；在网页编辑器里给一条加字再删掉几个、在最后打 `## ` 加一条新的；`tcms affine sync` 以后 git 里改了一条、加了一条（类型用默认的 `reference`），作者是 AFFiNE 账号的名字；在 git 里改两条（其中一条是网页里新加的）再 `sync`，重开网页看到的是改过的；再 `sync` 两边都没变。

这一步对着真 AFFiNE 跑时修了三处：

- 文件夹表在服务端的 id 是 `db$<工作区 id>$folders`（只写 `db$folders` 服务端不给读写）。`affine-doc` 的 `workspace::table_doc_id(工作区 id, 表名)` 拼这个（TCMS #32），`tcms-affine` 的 `folders_doc_id` 调它。
- `affine-sync-client` 被拒以后重新加入（7.2）。
- yrs 去掉 `small-client`（7.1）：网页版的客户端 id 超过 32 位，开着它时网页里删掉的字读出来还在（打 `## ` 变成标题时删掉的 `## ` 跟着进了 git）。加了一个测试，用 yjs 13.6.21 拿 50 位客户端 id 写的一小段更新。

还没做的：

- 文件开头（第一个二级标题前面的内容）只在接上时放进 AFFiNE，之后两边改了都不同步；没有二级标题的文件不接；AFFiNE 里改文档标题不改文件名；文件夹改名、挪动不管。
- 一次同步整个过程都拿着提交队列的锁，连 AFFiNE 的时间也在里面，这期间批准、改单条要等。A3b 一直跟着同步时改成了要写才拿锁（7.4）；`tcms affine sync` 还是一开始就拿（配了远端时要先拉）。
- 没加基准，在 A5（做了，7.7）。

### 7.4 A3b 做了什么（2026-11-25）

`tcms serve`（HTTP）设了 `TCMS_AFFINE_WORKSPACE`（和连 AFFiNE 的另外几个环境变量，7.3）时一直跟着同步；也可以 `tcms affine follow` 在前台跑（Ctrl-C 停）。代码在 `crates/tcms-affine/src/follow.rs`。

- **什么时候同步**：
  - AFFiNE 里有人改了一篇（同步协议推来的广播）：等这篇停下 10 秒没人再改再同步，一直有人在改的话从第一次改起最多等 2 分钟。工作区根文档、文件夹树改了也一样（新建文档、移进回收站、挪文件夹）。
  - git 里变了：每 30 秒看一次 HEAD，索引发了变更通知（`NOTIFY tcms_changes`：批准、改单条、`tcms reindex`、从远端拉下来）时马上看；HEAD 变了就比一遍每篇接上的文档在 HEAD 里的 blob 和上次同步完记下的，不一样的马上同步，整个接上的范围里有新的、接得上的文件也马上同步。
  - 刚开始、断线重连以后、每 5 分钟：全部看一遍，补上漏掉的广播。
  - 出错了：30 秒以后再来，没同步成的留着；同一个错只往日志写一次。
- **要写才拿锁**：每次同步先不拿提交队列的锁，从 AFFiNE 取差量、看 HEAD 里的 blob；两边都没变的文档就这样过去，不拿锁，这期间批准、改单条不用等 AFFiNE。要写 git、写 AFFiNE 或者改记下的同步状态时才拿（配了远端时先拉），拿到以后重新读一遍 HEAD 和四张表，手上这篇从头再看一次（记下的状态没变时，拿锁前取的差量接着用，不再取）。
- **每次同步看什么**：新文件、文件夹里的新文档、移进回收站的文档每次都看；接上的文档只看这次要看的那几篇。看完把工作区根文档、文件夹树、所有接上的文档都加入一遍（新接上的文档推的是新建，原来不收它的广播）。
- **日志**（标准错误）：只写有变化的文档；没接、停着的同一篇、同一个原因只写一次；连不上 AFFiNE 时 5 秒起每次翻倍、最多 5 分钟再连，不影响 MCP 和审核页。服务停的时候让手上那一次同步做完，最多等 20 秒。
- **在哪个线程**：跟着同步在 `tcms serve` 的主任务里和 HTTP 服务一起跑，没有另起线程；写 git 和批准、改单条一样排在提交队列里。

测试：

- `follow` 的 5 个单元测试只测排期（不连别的）：刚开始全部看一遍、停下 10 秒和最多等多久、git 里变了马上做、出错以后再来、重连以后全部看一遍时还在改的那篇留着。
- `tests/bridge.rs` 加了一个，对着内存里的假 AFFiNE 和真 PostgreSQL 跟着同步：广播来了写进 git、git 里提交了写进 AFFiNE、新加的文件接上；测试自己拿着提交队列的锁时来一个广播（两边都没变），照样很快看完。把跟着同步改成一开始就拿锁，这个测试就过不去（试过）。
- `tests/affine.rs` 加了一个，对着 Docker 里的 0.27.5-beta.3（定时全部看一遍关掉，只靠广播）：另一条连接改了进 git；另一条连接在文件夹里新建一篇，进 git 成新文件；新建过文档以后（之前的加入作废了，7.2）再改，照样收得到广播；git 里新加的文件接上以后，另一条连接改它也收得到；git 里改了，另一条连接读到。2026-11-25 跑过。

另外手动试了一遍（Docker 里的 0.27.5-beta.3，无头浏览器）：`tcms serve` 设了 `TCMS_AFFINE_WORKSPACE` 起来，日志写“连上了”；在网页编辑器里给一条加字、在最后打 `## ` 加一条，打完 10 秒后进了 git（一个提交，作者是 AFFiNE 账号的名字），检索索引跟着换了；在仓库里直接 `git commit` 改一条（没跑 `tcms reindex`），14 秒后（下一次看 HEAD 时）写进 AFFiNE，重开网页看到的是改过的；发 SIGTERM，半秒停下。

还没做的：

- 收广播靠的是加入过的文档；加入作废以后服务端照样推广播（上面的测试看到的），但这是 0.27.5-beta.3 上看到的，没有文档写着。每 5 分钟全部看一遍兜底。
- 工作区里“有文档变了”的通知（`space:broadcast-doc-invalidation`，自己推的也发）没用；没加入的文档靠文件夹树变了发现。
- 停着的文档、等人处理的条目只在日志里写一次，审核页里看（A4a 做了，7.5）。
- 没加基准，在 A5（做了，7.7）。

### 7.5 A4a 做了什么（2026-11-25）

审核页多了一页“和 AFFiNE 同步”（`#/affine`）：这个服务在跟着同步，或者接上过范围时才有这一页，标签上写着要人处理的有几件（等人处理的条目加上停着的文档）。代码在 `crates/tcms-review/src/affine.rs` 和网页的 `app.js`；跟着同步的一方和审核页共用一个 `FollowLink`（`crates/tcms-affine/src/follow.rs`）。

- **连接**：连着、在连、断了在重连，从什么时候起；上次同步、上次有改动是几分钟前；出了错写出来（下次同步成了就清掉）。都只在内存里，服务重启以后从头记。这个服务没跟着同步（没设 `TCMS_AFFINE_WORKSPACE`）时写明，下面照样列上次同步记下的。
- **等人处理的**：一条一块，git 的和 AFFiNE 的并排，各自和底稿（上次同步完两边一样的样子）按行比，底稿可以展开看。按原因给按钮，按钮下面写明下次同步时会怎样：
  - 两边都改了：留 git 的、留 AFFiNE 的、改出合并后的（标题、正文先填 git 里的，改好保存：先在 git 里改成那样，是一个提交，提交者是审核的人，和改单条一样排在提交队列里；再按“留 git 的”处理，下次同步写进 AFFiNE）。git 里这一条在记下以后又改过的，不让合并，叫人刷新。
  - AFFiNE 里删了、git 里改了：留下（重新写进 AFFiNE）、删掉（git 里也归档）。git 里删了、AFFiNE 里改了：删掉（AFFiNE 里也删）、留下（当成新加的写进 git）。
  - 只读的（AFFiNE 表示不全的写法）：只能改回 git 的；`tcms affine resolve --keep affine` 也不让了。写不过去的：再试一次、用 git 的。
- **停着的文档**：写着为什么停；点“看过了，接着做”，再问一句，确定以后和 `tcms affine sync --resume <路径>` 一样。要这个服务在跟着同步；没跟着同步时写明用命令行。
- **接上的文档**、**在 AFFiNE 里只能看的条目**（底稿里有表格、图片的，点进条目页）、**最近的**（`affine.` 开头的审计，最近 20 条）。
- **处理完马上同步**：处理一条以后让跟着同步的一方马上同步那一篇，不等广播、不等每 5 分钟全部看一遍；接着做的文件排着，同步成了才去掉（没成的下次再试）。没跟着同步时处理照样记下，下次 `tcms affine sync` 写过去。
- **审计**：处理一条记 `affine.resolve`（谁、哪个文件、哪一条、原因、留哪边），和改底稿在一个事务里；命令行的 `tcms affine resolve` 也记。接着做记 `affine.resume`（谁、哪个文件、停的原因）。
- **接口**：`GET /api/affine`，`POST /api/affine/conflicts/{id}/resolve`（`{"keep": "git" | "affine" | "merged", "title"?, "body"?}`），`POST /api/affine/docs/resume`（`{"path"}`）；`/api/me` 多了 `affine`（要不要显示这一页）。和别的接口一样要审核的人的令牌。
- **日志**：只记下了等人处理的、别的条目都没变的文档以前不写日志，现在写一行“别的条目两边都没变（N 条等人处理）”。

测试：

- `tcms-review` 的接口测试（真 PostgreSQL，存进去几行假的同步记录）：没接上时 `/api/me` 不显示这一页；没跟着同步时看得到、接着做回 409 叫人用命令行、只读的不能留 AFFiNE 的；跟着同步时改出合并后的（git 里一个提交、作者是审核的人、底稿换成 AFFiNE 的、排上马上同步那一篇），记下以后 git 里又改过的不让合并，接着做排上，审计里谁、留哪边都对。
- `tests/bridge.rs` 加了一个，对着内存里的假 AFFiNE：跟着同步的状态（连着、上次同步）对；不看 git、不定时全部看，处理完等人处理的叫一声马上写进 git；停着的文档叫一声接着做，同步成了才从排着的里去掉。

另外手动试了一遍（Docker 里的 0.27.5-beta.3，无头浏览器）：在 AFFiNE 网页里和 git 里各改同一条，把另一篇移进回收站，起 `tcms serve`；用审核的人的令牌登录审核页，“和 AFFiNE 同步（2）”里看到连着、那一条两边并排、那一篇停着；改出合并后的保存，git 里多了审核的人的提交，几秒后重开 AFFiNE 网页看到合并后的；停着的那篇点两下接着做，git 里归档；刷新以后标签上没有数字，“最近的”里有处理和接着做。浏览器控制台没有报错。

还没做的：

- 合并后的只能改正文和标题；“在 AFFiNE 里只能看的条目”按底稿算，git 里刚改成带表格、还没同步的不算。

- 没加基准，在 A5（做了，7.7）。

### 7.6 A4b 做了什么（2026-11-25）

agent 的提议在 AFFiNE 的文档上显示成评论（5.5）。代码在 `crates/tcms-affine/src/comments.rs`，评论的增删改在 `affine-sync-client` 的 GraphQL 里（多了回复 `createReply`、带链接的内容 `comment_spans`）。

- **发在哪篇上**：改、归档、取代一条的，发在这一条所在的文档上（按上次同步完记下的）；新建的，发在默认写进的文件（`<范围>/<类型>.md`）对应的文档上。目标不在接上的文档里的不发；后来接上了（比如新建的目标文件有了、整个范围接上以后接上了这个文件），下次看的时候发。
- **评论里写什么**：三段。“宏观研究员（岗位 macro）提议修改「CPI 从哪里取」，标题改成「…」。”（新加一条、修改、归档、取代、提到别的范围各有说法）；“理由：”后面是理由的前 200 个字；“批准、拒绝在审核页：打开这条提议”，链接是 `<TCMS_PUBLIC_URL>/review#/proposals/<提议 id>`，没设 `TCMS_PUBLIC_URL` 时写提议 id。不放正文和证据（证据里可能有对话链接）。评论的预览是这一条现在的标题。
- **不挂在文字上**：评论不改文档，在网页版文档右边栏的“评论”里看（2026-11-25 在 0.27.5-beta.3 的网页里看过，不挂在文字上的评论也列在那里）。挂在文字上要改文档里的文字属性，第一版不做。
- **批准、拒绝以后**：在评论下回复一句结果（“已接受（王审核），写进了上下文仓库，提交 1a2b3c4d5e6f。”“已拒绝（王审核）：先不改”），再标成已解决。回复了、标成已解决时出错的，下次只标成已解决，不再回复一遍。
- **人在 AFFiNE 里的回复**：看的时候取一遍那篇文档上的评论，把这条评论下人的回复（谁、什么时候、写了什么；不算自己回复的结果）记下来，审核页这条提议下面列出来（“AFFiNE 里的评论”）。第一版只列出来，不当成对提议的修改。
- **评论在 AFFiNE 里被删了**：不再管，也不再发。
- **记在哪里**：新表 `affine_comments`（迁移 0008）：提议 id、工作区、文档、文件、评论 id、关了没有、人的回复。提议删掉时跟着删。
- **什么时候看**：跟着同步时，提议建了、批准了、拒绝了（存提议、记处理结果的事务里 `NOTIFY tcms_proposals`，内容是 schema 名）停 2 秒看一遍（agent 常常一连提几条）；每次全部看一遍（每 5 分钟）以后也看一遍，顺便取回人的回复。`tcms affine sync`、`resolve` 同步完也看一遍，输出里写发了几条、关了几条。一条一条发、回复时出的错记下来，别的照做，下次再试；同一个错日志里只写一次。
- **设置**：`TCMS_PUBLIC_URL`，审核页对外的地址（比如 `https://ctx.example.com`），可选。

测试：

- `tests/bridge.rs` 加了三个，对着内存里的假 AFFiNE 和真 PostgreSQL：
  - 改一条、归档一条发在各自的文档上，评论的字、链接、预览对，没有正文和证据；新建的目标文件还没有时不发；再看一遍什么都不做；人回复了记下来；拒绝一条、批准一条以后回复结果（提交号对）、标成已解决，自己回复的不算人的回复；新建的目标文件在 git 里有了、同步接上以后发；评论被删了记成删了，以后不再发。

  - 跟着同步时（不看 git、不定时全部看），提议存进来几秒内发了评论，拒绝以后几秒内回复结果、标成已解决。

- `tests/affine.rs` 加了一个，对着 Docker 里的 0.27.5-beta.3：发评论（链接对），同一个账号回复一句，记下来；拒绝以后回复结果、标成已解决，再看一遍什么都不做。2026-11-25 跑过。

### 7.7 A5 做了什么（2026-11-25）

`tcms bench affine [--items N] [--edits N] [--check]`（`crates/tcms-cli/src/bench/affine_sync.rs`），CI 里带 `--check` 跑。上下文仓库在临时目录里，PostgreSQL 用临时 schema，AFFiNE 换成同一个进程里的假 AFFiNE（内存里的 Yjs 文档，收发更新、存评论），量的是本系统这一侧；连真的 AFFiNE 时还要加上网络往返（取、推一篇各一次），这里量不到。默认 1 千条：一个范围、50 个文件、每个文件 20 条（一段带粗体的正文加一个两项的列表）。

量的几项（门槛和实测在 `architecture.md` 第 10 节）：

- 第一次接上 1 千条：建文件夹和 50 篇文档、写进 AFFiNE、记下底稿。
- 全部看一遍、两边都没变（跟着同步时每 5 分钟一次）：接上以后第一次每篇都取，单独报一个数；之后 AFFiNE 说最后改的时间没变的不取（7.11），跑 10 次。两个用同一个门槛。
- 跟着同步（`follow`，等人停手的 10 秒改成 0，量的是本系统处理的时间）：AFFiNE 里改一条，从收到广播到 git 里提交完；git 里改一条，从提交、更新索引（发变更通知）到写进 AFFiNE。各改 30 次，一次做完再改下一次。
- 跟着同步多用的物理内存：开始跟着同步之前（接上、全部看过以后，等稳下来）和跟着同步改完、空闲下来以后比。假 AFFiNE 的文档也在这个进程里，只有差值有意思。
- 提议显示成评论：给 100 条提议发评论（每篇文档两条），再看 10 遍（都发过了，只取回复）。

2026-11-25 在云端开发机（4 核，本地 PostgreSQL 16，release）跑了几遍，1 千条时每项都在门槛的五分之一以内；跟着同步、空闲以后比开始之前多 -6 到 3 MB，没有越用越多。

另外用 `--items 10000`（500 篇文档）跑了一遍，没设门槛：第一次接上 3.3 秒；全部看一遍中位数 520 毫秒；AFFiNE 里改一条到提交完中位数 180 毫秒、git 里改一条到写进 AFFiNE 中位数 220 毫秒；看一遍评论 71 毫秒；跟着同步多用约 5 MB。改一条的时间随条数涨，量下来主要花在每次同步开头和拿锁以后各把所有文档的同步状态、所有条目的底稿从 PostgreSQL 取一遍（1 万条时每次约 50 毫秒）。下面 7.8 改了。

### 7.8 1 万条时只取要同步的几篇（2026-11-25）

A5 做完以后维护者选了这一步。临时加计时量的（1 万条、500 篇文档）：所有文档的同步状态一共 13 MB，取一遍 34 到 49 毫秒；所有条目的底稿取一遍 20 到 26 毫秒；等人处理的不到 1 毫秒。跟着同步时改一条，这些在同步开头和拿锁以后各取一遍；同步完为了收新文档的广播、看 git 有没有变，又各把所有文档取一遍（连着状态）。

改成：

- `affine_docs` 不再带 Yjs 状态，只有路径、文档 id、git blob、停着的原因这些（`AffineDoc` 里没有 `state` 了，存的时候放在 `AffineSave.state`）。
- 同步时只取要同步的几篇的状态（`affine_doc_states`，一次取齐）；拿锁以后取过的几篇重新取，别处刚存过的不会用旧的。全部看一遍时还是取所有的。
- 底稿和等人处理的在拿着锁、要比较那一篇时只取那一篇的（`affine_bases_at`、`affine_conflicts_at`）。两边都没变的文档不取。
- 看一遍评论时，底稿只取还没发评论的提议针对的那几条（`affine_bases_of`），不再取所有条目的。

结果（云端开发机，4 核，本地 PostgreSQL 16，release，假 AFFiNE）：

### 7.9 对着真 AFFiNE 量（2026-11-25）

7.7、7.8 的数都是假 AFFiNE 量的，不含网络往返。`tcms bench affine --real` 换成真的 AFFiNE：连 `TCMS_AFFINE_URL`、`TCMS_AFFINE_EMAIL`、`TCMS_AFFINE_PASSWORD` 指的 AFFiNE（和 `tcms serve` 一样），每跑一次新建一个工作区“TCMS 基准”（不删），“人在 AFFiNE 里改”用另一条同步连接取来、改了、推上去（和网页编辑器推的一样是 Yjs 更新），从推之前开始算，收广播、取、推都走网络。门槛是按假 AFFiNE 定的，`--real` 不比门槛，也不能带 `--check`。CI 里没有 AFFiNE，不跑。一次要登录两次（同步程序、模拟的人），连着跑要隔一分钟左右（7.2 的登录限流）。

2026-11-25 在云端开发机上对着同一台机器 Docker 里的 AFFiNE 0.27.5-beta.3 跑了：1 千条三遍，1 万条一遍（每边改 20 次）。网络往返只是本机回环，换成另一台机器上的 AFFiNE 会更慢。

| 第一次接上 | 0.28 到 0.30 秒 | 2.5 到 2.7 秒 | 23.9 秒 |
| 全部看一遍、两边都没变 | 中位数 17 到 20 毫秒 | 中位数 165 到 187 毫秒，p95 362 到 424 毫秒 | 中位数 1.83 秒，p95 3.47 秒 |
| AFFiNE 里改一条到提交完 | 中位数 14 到 16 毫秒 | 中位数 52 到 59 毫秒，p95 64 到 74 毫秒 | 中位数 116 毫秒，p95 137 毫秒 |

看出来的几点（还没改）：

- **改一条**：1 千条时两边都在 60 毫秒以内，比等人停手的 10 秒小得多。1 万条时翻了一倍。同步一次都要把工作区根文档（所有文档的列表）和文件夹树整篇取一遍（`Workspace::load` 不带状态向量），1 万条时这两篇各有 500 项；多出来的时间多半在这里，没细量。2026-11-26 细量了，最多的不在这里，见 7.12。
- **全部看一遍**：一篇一篇取，平均每篇约 3.5 毫秒，1 万条时要 1.8 秒，每 5 分钟一次。跟着同步时这期间收到的改动要等它做完。可以先用 `space:load-doc-timestamps` 问哪些文档上次以后变过，只取变了的。2026-11-26 改了，见 7.11。
- **看一遍评论**：有没关的评论的文档，一篇问一次 GraphQL，这里是 50 篇，平均每篇约 21 毫秒（1.07 秒 ÷ 50 篇算的），一遍要 1 秒多。提议一有变化 2 秒后就看一遍，全部看一遍以后也看一遍，期间收到的改动也要等。可以几篇一起问，或者只问提议有变化的那几篇。2026-11-26 改成几篇一起问，见 7.10。
- 第一次接上 1 万条要 24 秒，只做一次，先不管。

### 7.10 看一遍评论一次问几篇（2026-11-26）

7.9 看出来的第三点。#42 合并后卡片上推荐改“一篇一篇问”的两处（开 PR 时维护者还没选，先按推荐做；维护者后来选了这一项），这是第一处，第二处见 7.11。

- `affine-sync-client` 加了 `Client::comments_of(工作区, 文档 id 列表)`：同一个 `comments` 字段用 GraphQL 别名在一次查询里问几遍，一次问 25 篇（`DOCS_PER_QUERY`），每篇都在结果里，没有的文档是空的。AFFiNE 接受这种写法，是对着 0.27.5-beta.3 试出来的。
- 同步程序的 `Affine` 加了 `comments_of`：默认一篇一篇问（测试和基准里的假 AFFiNE 用它），连真 AFFiNE 时用上面那个。看一遍评论时发过、还没关的那几篇一次取齐；一次取出错时一篇一篇取，一篇的错不耽误别的。
- 另外发现 AFFiNE 0.27.5-beta.3 的评论在最后一页也说 `hasNextPage: true`：一篇 2 条评论，取 100 条，回来 2 条，`hasNextPage` 还是 `true`。原来的 `comments` 每篇都要多问一次空的下一页。现在多取一个 `totalCount`，按它判断还有没有下一页，`comments` 和 `comments_of` 都是。

对着同一台机器 Docker 里的 AFFiNE 0.27.5-beta.3 跑 `tcms bench affine --real`（1 千条、50 篇文档、100 条评论都发过），看一遍评论从中位数 1.07 到 1.12 秒降到 0.21 秒（两遍，p95 257 到 262 毫秒）。单独用脚本量过 GraphQL：一次问 25 篇约 100 毫秒，一篇一次约 10 毫秒。

### 7.11 全部看一遍只取变了的（2026-11-26）

7.9 看出来的第二点，#42 合并后卡片上推荐的两处里的第二处（维护者选了这一项）。

- 全部看一遍（刚开始、重连以后、每 5 分钟，还有 `tcms affine sync`）先用同步协议的 `space:load-doc-timestamps` 问一次工作区里每篇文档在 AFFiNE 里最后改的时间（毫秒，AFFiNE 服务端的钟），一次回来全部。
- `affine_docs` 加了一列 `affine_ts`（迁移 `0009_affine_doc_ts.sql`）：一篇文档全部看一遍时取了、两边都没变，记下这次问到的它的时间。存这篇的同步结果（推了、拉了）、停下、处理两边都改了的时候清掉。
- 下次全部看一遍时，记下的时间和这次问到的一样、git 里的 blob 也和上次同步完一样、没停着、不在要接着做的里面、没移进回收站的，这篇不取，直接算“没变”。别的照原样取。
- 记的是取之前问到的时间：问完到取完之间人又改了，取回来的就有这次改的，不算“没变”，不记；取完以后再改的，时间比记下的新，下次会取。
- 问不到时间（出错，或者 `Affine` 的实现没有这一项）就每篇都取，和原来一样。只同步几篇的时候（跟着同步收到广播、git 里变了）不问。
- 工作区根文档和文件夹树照旧每次都整篇取（7.9 的第一点，没改）。
- 测试里的假 AFFiNE 拿整篇状态的哈希当“最后改的时间”：只删了东西时 Yjs 的状态向量不变，用状态向量会漏掉。基准里的假 AFFiNE 每推一次、模拟的人每改一次加一。

测试：`tests/bridge.rs` 加了 `full_sync_skips_unchanged_docs`（假 AFFiNE）：接上以后第一次全部看一遍每篇都取，记下时间；再看一遍只取根文档和文件夹树；AFFiNE 里改一篇只取那篇，下次再取一次、记下；git 里改一篇，AFFiNE 说的时间没变也取，改动推过去。`tests/affine.rs` 的 `sync_with_a_real_affine` 对着 Docker 里的 0.27.5-beta.3 加了几步：两边都没变时记下的时间和 AFFiNE 回的一样；另一条连接推了修改以后 AFFiNE 回的时间变了，全部看一遍照样取到、进 git。

基准：`tcms bench affine` 把接上以后第一次全部看一遍（每篇都取，和改之前一样）单独报，也用全部看一遍的门槛；之后的 10 次量的是只取变了的。2026-11-26 在云端开发机上跑的（真 AFFiNE 是同一台机器 Docker 里的 0.27.5-beta.3，1 万条时每边改 20 次）：

| 全部看一遍、两边都没变 | 改之前 | 改之后，接上以后第一次（每篇都取） | 改之后，之后几次 |
| --- | --- | --- | --- |
| 1 千条，假 AFFiNE | 中位数 17 到 20 毫秒（7.8） | 21 到 28 毫秒 | 中位数 1.2 到 1.7 毫秒，p95 1.9 到 2.9 毫秒 |
| 1 万条，假 AFFiNE | 中位数 430 到 520 毫秒（7.8） | 445 到 529 毫秒 | 中位数 7.2 到 7.6 毫秒，p95 8.4 到 9.5 毫秒 |

### 7.12 1 万条时改一条慢在哪（2026-11-26）

7.9 看出来的第一点：AFFiNE 里改一条到提交完，1 千条时约 55 毫秒，1 万条时翻了一倍。#44 合并后卡片上推荐查这一项（开 PR 时维护者还没选，先按推荐做）。

临时加了计时，对着同一台机器 Docker 里的 0.27.5-beta.3 跑 `tcms bench affine --real --items 10000`，跟着同步时一次（约 100 毫秒）花在：

| 哪一步 | 1 万条，真 AFFiNE | 1 万条，假 AFFiNE |
| --- | --- | --- |
| 整篇取工作区根文档和文件夹树（`Workspace::load`） | 9 到 15 毫秒 | 3 到 5 毫秒 |
| 读接上的文档和范围、看 git 里有没有新文件、列出要同步的 | 约 5 毫秒 | 约 5 毫秒 |
| 这一篇：取差量、拿锁、改文件、提交、存同步结果（不算下一行） | 约 20 毫秒 | 约 17 毫秒 |
| 问这一篇是谁改的（GraphQL 取最近改过的 100 篇，再取工作区成员） | 约 40 毫秒 | 不问 |
| 提交以后更新索引（`tcms-write` 的 `Batch::finish`；要取所有条目的状态） | 约 22 毫秒 | 约 22 毫秒 |

最多的是问作者。另外单独用脚本对着同一个 AFFiNE、500 篇文档的工作区量过 GraphQL（含起 curl 约 5.5 毫秒）：最近改过的 100 篇约 32 毫秒，工作区成员约 12 毫秒；只问一篇 `workspace.doc(docId).lastUpdatedBy.name` 约 18 毫秒。

改成：

- `affine-sync-client` 加了 `Client::last_updated_by(工作区, 文档)`：只问这一篇最后是谁改的，回来的就是名字，不用再对成员表。服务端还没有这篇（`DOC_NOT_FOUND`）时是 `None`。
- `Affine` 的 `editors(工作区)`（最近改过的文档 → 名字）换成 `editor(工作区, 文档)`。一次同步里每篇只问一次，记下来；拿不到照旧写“AFFiNE”。
- 一次同步里 AFFiNE 那边改了好几篇时（比如重连以后），原来问一次，现在每篇问一次（各约 12 毫秒）。这种时候少，先不管。

索引那一步是 TCMS 自己的增量索引（`architecture.md` 第 10 节“一个只改了一个文件的提交，到索引更新完”），批准一条也走它，不在这次改。根文档和文件夹树每次整篇取，假 AFFiNE 上 3 到 5 毫秒、真 AFFiNE 上多 6 到 10 毫秒，还没改。

改了以后跑 `tcms bench affine --real`（AFFiNE 里改一条到提交完）：

| | 改之前 | 改之后 |
| --- | --- | --- |
| 1 千条 | 中位数 52 到 59 毫秒（7.9），57.7 到 58.3 毫秒（7.11 时） | 中位数 42.1 到 44.8 毫秒，p95 52.5 到 60.2 毫秒（两遍） |
| 1 万条 | 中位数 116 毫秒（7.9），106.7 毫秒（7.11 时），加计时那两遍 92 到 120 毫秒 | 中位数 68.6 到 97.3 毫秒（两遍，每边改 20 次） |

1 万条的两遍差得多：第二遍别的几项也都慢（不问作者的“git 里改一条到写进 AFFiNE”也从 56 毫秒到 78 毫秒，第一次接上 26 秒到 29 秒），这台 AFFiNE 里基准建的工作区越积越多，没细查。同一遍里拿“AFFiNE 里改一条”减“git 里改一条”比，改之前三遍多 33 到 46 毫秒，改之后两遍多 12 到 20 毫秒，省下的和上面单独量的 GraphQL 对得上。别的几项和 7.11 差不多。假 AFFiNE 不问作者，数没变。

## 8. 已定的事（2026-11-24，维护者在卡片上选了“都按推荐定”）

1. **走哪条路**：甲，同步协议加 `yrs`。如果 AFFiNE 的读写 MCP 凭据进了正式版、读回来能带块 id，对应表和同步循环不动，连接那一层可以换成乙，到时候再问。
2. **范围怎么放**：一个专门的工作区，一个范围一个文件夹，一个文件一篇文档。
3. **条目的属性**（类型、复核日期、标签、负责人）：第一版不放进 AFFiNE，只在 Markdown 和审核页里改；以后可以用文档的自定义属性或者标题块下面一行小字。
4. **AFFiNE 里删掉一条**：照 Markdown 的规矩算归档，一次删掉一篇文档一半以上的条目时停下来等人确认。
5. **两边都改了同一条**：不自动合，暂停这一条，在审核页并排给人选（第 5.4 节）。
6. **提议显示成评论**：做（A4），评论里只放动作、标题、理由的开头和审核页链接。
7. **先支持哪个 AFFiNE 版本**：从 0.27.5 起，自托管版（2026-11-24 查：0.27.5 还只有测试版 `0.27.5-beta.3`，正式镜像 `stable` 还是 0.27.4；同步协议的批量加入要 0.27.5，所以先对着测试版测，正式版出来再跑一遍）。AFFiNE Cloud 上的工作区能不能接、条款允不允许第三方客户端走同步协议，还没查，接 Cloud 之前先查。
